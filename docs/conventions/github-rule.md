# 🌐 GitHub 협업 규칙

본 문서는 MOAMOA Backend 팀의 협업 품질(가독성/안정성/속도)을 위해 **커밋/브랜치/PR/리뷰** 규칙을 정의합니다.  
리뷰는 **CodeRabbit(자동) + 페어 리뷰어(사람)**를 기본으로 합니다.

## 1. 커밋 규칙

### 1.1 커밋 메시지 형식
커밋 메시지는 반드시 **작업 타입 + 간단한 설명** 형식으로 작성합니다.

<type>: <subject>

- subject는 50자 내외, “무엇을 했는지”가 보이게 작성
- 팀 합의 시 scope 확장도 허용: `feat(member): ...` (선택)

### 1.2 타입 목록
| 타입 | 설명 |
|---|---|
| feat | 새로운 기능 추가 |
| hotfix | 치명적 버그 수정(운영 긴급) |
| fix | 버그/단순 코드 수정 |
| refactor | 코드 리팩토링(기능 변화 없음) |
| move | 파일/폴더 이동 및 구조 정리 |
| del | 기능/파일 삭제 |
| test | 테스트 코드 작성/수정 |
| gitfix | .gitignore 수정 |
| script | 빌드/패키지/환경 설정 관련 수정 |
| rename | 파일 및 코드 이름 수정 |
| docs | 문서 수정(README, 컨벤션, 위키 등) |
| chore | 기타 잡무(설정 정리, 버전업 등) |

### 1.3 예시
- `feat: User 엔티티 및 레포지토리 생성`
- `fix: 토큰 재발급 로직 NPE 수정`
- `refactor: 결제 상태 전이 로직 정리`
- `docs: GitHub 협업 규칙 문서 업데이트`

## 2. 브랜치 규칙

### 2.1 브랜치 역할
- `main`
  - 운영(Production) 배포 브랜치
  - 직접 커밋 금지 ❌ (PR로만 병합)
- `dev`
  - 개발 통합 브랜치
  - 모든 작업 브랜치의 기본 병합 대상
- 작업 브랜치
  - `dev`에서 분기 → 작업 → `dev`로 PR
- `hotfix/*`
  - 운영 긴급 수정 브랜치
  - `main`에서 분기 → `main`에 병합
  - 병합 후 **동일 변경을 dev에도 반영(PR 또는 merge)**

### 2.2 브랜치 네이밍
**형식**
<type>/<work-desc>/#<issue-number>

- `<type>`: `feat | fix | refactor | docs | chore | hotfix`
- `<work-desc>`: 영문 소문자 + kebab-case 권장 (`token-refresh`, `member-signup`)
- 이슈가 없으면 `#0` 허용(팀 합의)

**예시**
- `feat/login/#12`
- `fix/token-refresh/#34`
- `refactor/member-domain/#57`
- `chore/github-actions/#3`

## 3. Pull Request 규칙

### 3.1 PR 생성 기본
- PR 대상 브랜치: **dev**
- PR 제목 권장: `type: 작업 요약`
  - 예) `feat: 유저 도메인 엔티티 및 레포지토리 생성`
- PR에는 반드시 아래를 포함
  - 변경 요약(무엇)
  - 변경 이유(왜)
  - 테스트/검증 방법(어떻게)

### 3.2 PR 템플릿 사용
- 파일 위치: `.github/PULL_REQUEST_TEMPLATE.md`
- PR 만들면 자동으로 템플릿이 뜨게 됩니다.

### 3.3 머지 조건(필수)
머지 전 아래 3개를 만족해야 합니다.
- [ ] **CodeRabbit 코멘트 확인/반영(또는 근거 작성)**
- [ ] **페어 리뷰어(사람) 승인 1명 이상**
- [ ] **CI 통과(빌드/테스트)**

## 4. 리뷰 운영 규칙 (CodeRabbit + 페어 리뷰)

### 4.1 팀 운영 방식(5명)
- 팀은 **2인 페어**로 작업합니다.
  - Driver: 코드 작성
  - Reviewer: 코드 검토/보조
- 5명이라 **한 명이 2개 페어에 속할 수 있습니다.**
- 각 PR은 원칙적으로 **해당 작업의 “리뷰 담당자(페어 Reviewer)”가 1차 책임 리뷰어**입니다.

### 4.2 리뷰 기준
- CodeRabbit 지적 중 “버그 가능성/보안/명확한 개선”은 반드시 반영 또는 근거를 남깁니다.
- DB 변경 / Security 변경은 **승인 2명 권장**(팀 합의 시 필수로 올려도 됨).

### 4.3 리뷰 처리 원칙
- 코멘트는 “수정 반영” 또는 “근거 포함 설명” 중 하나로 반드시 처리합니다.
- 수정 후 리뷰어에게 re-request review 합니다.

---

## 5. 기타 규칙
- `main` 브랜치는 항상 배포 가능한 상태 유지
- 불필요한 파일/코드는 머지 전 정리
- 규칙에 없는 상황은 팀 합의 후 문서에 반영
